# 001 - Jira Project Routing Per Grundet Project

**Date:** 2026-05-01  
**Status:** Accepted

## Context

Current Jira export routing is team-wide:

- Jira OAuth connection is stored per team (`JiraConnections`).
- Jira destination project key is also stored per team (`JiraConnections.JiraProjectKey`).
- Export of any work item in that team uses that single key.

This is insufficient for multi-project teams. A team can have multiple Grundet projects, and each can need a different Jira project key.

Additional constraints:

- Global app OAuth credentials (`Jira:ClientId`, `Jira:ClientSecret`, `Jira:RedirectUri`) remain app-level config, not tenant-level data.
- Tenant-specific credentials (tokens/site) remain in DB and must stay team-scoped.
- Export routing must be deterministic from `WorkItem.ProjectId`.
- Existing API clients may still call `PUT /teams/{teamId}/jira/project` and parse `GET /teams/{teamId}/jira/connection`.

## Decision

Introduce explicit Jira project mapping per Grundet project, with optional team-level default fallback.

1. Keep OAuth app credentials global in config/env.
2. Keep Jira OAuth connection tokens per team in `JiraConnections`.
3. Add a new table for explicit per-project mapping.
4. Reinterpret `JiraConnections.JiraProjectKey` as optional team default (fallback only).
5. Resolve export target in this order:
- explicit mapping for `WorkItem.ProjectId`
- team-level default project key
- fail with setup guidance
6. Preserve wire compatibility in phase 1:
- keep `PUT /teams/{teamId}/jira/project` (default key semantics)
- keep missing-routing export error as `400 + ProblemTypes.Validation`

## Schema Changes

### New table: `JiraProjectMappings`

Purpose: map one Grundet project to one Jira project key, while enabling safe team-scoped cleanup without depending on `Projects` query filters.

Columns:

- `TeamId uuid` (not null)
- `ProjectId uuid` (not null)
- `JiraProjectKey text` (not null)
- `CreatedAt timestamp with time zone` (not null)
- `UpdatedAt timestamp with time zone` (not null)

Constraints/indexes:

- `PK_JiraProjectMappings(TeamId, ProjectId)`
- `UX_JiraProjectMappings_ProjectId` (unique)
- `FK_JiraProjectMappings_Teams_TeamId` -> `Teams.Id`
- `FK_JiraProjectMappings_Projects_ProjectId_TeamId` -> `Projects(Id, TeamId)`

Additional model key:

- Add alternate key (or unique constraint) on `Projects(Id, TeamId)` to support composite FK.

Rationale:

- Team-scoped delete/list operations can run directly on `JiraProjectMappings.TeamId`, including when projects are soft-deleted.
- Composite FK prevents mismatched `TeamId`/`ProjectId` pairs.

### Existing table: `JiraConnections`

No physical column rename in phase 1.

- Keep column name `JiraProjectKey` for migration safety.
- Semantics change to: `DefaultJiraProjectKey` (team fallback only).
- Code-level naming should move to `DefaultJiraProjectKey` where possible.

### EF model additions

- Add `DbSet<JiraProjectMapping>` in `AppDbContext`.
- Add entity configuration in `OnModelCreating`.
- Add migration generated by EF Core (no manual schema edits).

## API Changes

### New project-scoped endpoints (primary contract)

All require project authorization via `RequireProjectAccessAsync`.

1. `GET /projects/{projectId}/jira/project`
- Returns effective mapping for one project.
- Response shape:
  - `projectId: guid`
  - `projectKey: string | null`
  - `source: "Explicit" | "TeamDefault" | "None"`

2. `PUT /projects/{projectId}/jira/project`
- Sets explicit mapping for one project.
- Body: `{ "projectKey": "ABC" }`
- Requires team Jira connection to exist.
- Response: `204 No Content`.

3. `DELETE /projects/{projectId}/jira/project`
- Removes explicit mapping for one project.
- Response: `204 No Content`.

### Team-scoped listing endpoint

Requires `RequireTeamAccessAsync` with at least `Contributor`.

4. `GET /teams/{teamId}/jira/project-mappings`
- Returns explicit mappings for active projects in the team.
- Response items:
  - `projectId: guid`
  - `projectName: string`
  - `projectKey: string`

### Team default endpoint strategy

Keep backward compatibility in phase 1:

5. Keep `PUT /teams/{teamId}/jira/project`
- Semantics become "set team default Jira project key".
- Documented as fallback configuration.
- Mark endpoint as deprecated in docs once project-scoped endpoints are adopted.

Optional additive clarity endpoint (same behavior):

6. `PUT /teams/{teamId}/jira/default-project`
7. `DELETE /teams/{teamId}/jira/default-project`

If added, existing route remains supported until explicit deprecation window ends.

### Connection status compatibility

`GET /teams/{teamId}/jira/connection` remains in phase 1, but `projectKey` is fallback-only.

- It must no longer be documented as the effective export target.
- Effective target is reported by `GET /projects/{projectId}/jira/project`.

## Service and Store Contract Changes

### `JiraExportWorkItem` record

Add `ProjectId` so export resolution does not require extra lookup round-trips.

From:

- `WorkItemId, TeamId, Title, Description, Requirements`

To:

- `WorkItemId, TeamId, ProjectId, Title, Description, Requirements`

### `IJiraStore` additions

- `Task<JiraProjectMappingRecord?> GetProjectMappingAsync(Guid projectId, CancellationToken ct = default)`
- `Task UpsertProjectMappingAsync(Guid teamId, Guid projectId, string projectKey, CancellationToken ct = default)`
- `Task DeleteProjectMappingAsync(Guid projectId, CancellationToken ct = default)`
- `Task<IReadOnlyList<JiraProjectMappingListItem>> GetProjectMappingsAsync(Guid teamId, CancellationToken ct = default)`
- `Task DeleteProjectMappingsForTeamAsync(Guid teamId, CancellationToken ct = default)`

### Export resolution algorithm (`JiraService.ExportWorkItemAsync`)

1. Load export work item (`TeamId`, `ProjectId`, details).
2. Ensure Jira connection and token freshness for team.
3. Try explicit mapping by `ProjectId`.
4. If none, try `connection.DefaultJiraProjectKey` (currently backed by `JiraProjectKey` column).
5. If none, throw missing-routing error (phase 1: `400 + ProblemTypes.Validation`).
6. Build Jira payload using resolved key.

### Connection lifecycle safety

To avoid stale mappings after Jira site changes:

- On `DELETE /teams/{teamId}/jira/connection`: delete team project mappings in the same DB transaction as connection delete.
- On OAuth callback/upsert: if existing `CloudId` differs from new `CloudId`, delete team mappings and upsert connection in one DB transaction.

This prevents accidental reuse of keys from a previous Jira site and avoids partial state.

## Validation and Error Contracts

### Project key validation

Normalize to upper-case and trim, then validate:

- regex: `^[A-Z][A-Z0-9_]{0,31}$` (adjust max length if needed)

On invalid key:

- `400 Bad Request`
- `ProblemTypes.Validation`

### Missing routing

Phase 1 compatibility decision:

- Keep `400 Bad Request`
- Keep `ProblemTypes.Validation`
- Update detail to mention project-scoped mapping endpoint first.

Optional phase 2 change (breaking unless versioned):

- move to `409 Conflict`
- new problem type: `https://grundet.app/errors/jira-project-mapping-required`

### Missing connection

No change:

- `409 Conflict`
- `ProblemTypes.JiraConnectionRequired`

## Authorization Model

- Team-wide endpoints (`connect`, `callback`, `connection`, `projects list`, `connection delete`, `team defaults`) stay team-authorized.
- Project mapping endpoints must be project-authorized (`AuthorizedProjectId`) to preserve tenant boundaries and per-project role checks.
- Export remains work-item-authorized (`AuthorizedWorkItemId`), then derives project/team internally from store lookup.

## Migration Plan

1. Add entity `JiraProjectMapping` and EF configuration.
2. Add `Projects(Id, TeamId)` alternate key/unique constraint for composite FK.
3. Generate migration to create `JiraProjectMappings` with constraints and indexes.
4. Keep existing `JiraConnections.JiraProjectKey` column unchanged.
5. Deploy without data backfill (existing value remains fallback).
6. Release API additions and compatibility behavior.
7. Later optional migration: rename DB column `JiraProjectKey` -> `DefaultJiraProjectKey` once clients/code are fully aligned.

Rollback behavior:

- Dropping `JiraProjectMappings` reverts to team-default-only routing.
- No destructive changes to existing Jira connection data in phase 1.

## Testing Plan

### Unit/service tests

- Export uses explicit project mapping when present.
- Export falls back to team default when explicit mapping absent.
- Export returns 400 when neither mapping nor default exists (phase 1 compatibility).
- Invalid project key returns 400.
- CloudId change clears mappings transactionally.

### Integration tests

- Project endpoint auth: contributor can read; lead required for write/delete.
- Team endpoint auth unchanged.
- Mapping CRUD persists and is isolated by project/team.
- Export for two work items in different Grundet projects routes to different Jira keys.
- Connection delete removes team mappings, including mappings for soft-deleted projects.

### Regression checks

- Existing `PUT /teams/{teamId}/jira/project` still works and sets fallback.
- Existing `GET /teams/{teamId}/jira/connection` still returns `projectKey` (fallback semantics).
- Existing Jira connection flow unchanged.

## Alternatives Considered

1. Keep team-only mapping
- Rejected: cannot support multi-project routing correctly.

2. Keep `ProjectId`-only mapping table and join via `Projects`
- Rejected for phase 1 due cleanup/listing ambiguity with soft-delete query filters.

3. Store Jira project key on `Projects` table directly
- Rejected for phase 1 because it couples integration configuration into core project entity and makes integration lifecycle changes noisier.

4. Remove team default immediately
- Rejected for rollout risk and compatibility; fallback is useful during incremental setup.

## Consequences

Positive:

- Correct multi-project Jira routing.
- Clear ownership boundary: global app OAuth config vs per-team OAuth tokens vs per-project routing.
- Safe cleanup behavior across Jira site reconnection and soft-deleted project state.

Trade-offs:

- More API and store/service surface area.
- Additional migration and test matrix.
- Temporary semantic mismatch while DB column name remains `JiraProjectKey`.

## Recommendation

Proceed with this phase-1 design, including compatibility-preserving error behavior and transactional cleanup on connection/site changes. It fixes multi-tenant routing correctness now without forcing immediate client breakage.
